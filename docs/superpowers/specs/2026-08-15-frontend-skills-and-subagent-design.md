# Frontend Skills Expansion + `frontend-design` Subagent — Design

## Context

User pointed at four external resources and asked what could help their coding
agent with UI/UX and web design:

1. `claudemarketplaces.com/skills/supercent-io/skills-template` — an installer
   pointing at a 78-skill catalog (not content itself).
2. `raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md`
   — a checklist covering accessibility, forms, animation, typography, images,
   performance, navigation/state, touch, dark mode, i18n, hydration safety,
   content/copy.
3. `claudemarketplaces.com/skills/giuseppe-trisciuoglio/developer-kit/tailwind-css-patterns`
   — Tailwind utility recipes (cards/forms/grids/nav, dark mode, responsive).
4. `claudemarketplaces.com/skills/vercel-labs/agent-skills/vercel-react-best-practices`
   — 69 React/Next.js performance checks with before/after examples.

An `Explore` survey of the existing `~/.claude` skill library found:

- **Accessibility is already deep**: `senior-engineering-partner/references/ui-design-and-accessibility.md`
  is a full WCAG 2.2 AA reference with a CI testing gate. The Vercel checklist's
  ARIA/contrast/focus content would be redundant there.
- **React perf and Tailwind patterns are confirmed gaps** — zero existing
  coverage anywhere in the repo (`grep -r hydration` across all skills: zero
  hits).
- **The taste-skill routing table is aesthetic-based** (which visual style to
  use), not concern-based (correctness/perf/patterns) — no natural slot for
  this content in its current form.
- `design-taste-frontend` is already ~1200 lines, past the house size
  guidance for a single `SKILL.md` — new content should not inline there.

The user then asked to also scan resource #1's 78-skill catalog for anything
else worth incorporating, beyond UI/UX. Of the names shortlisted and checked
in detail, `web-design-guidelines` turned out to be a wrapper that fetches the
same Vercel guidelines repo already in scope (duplicate, dropped). Three
others were confirmed as real, distinct gaps and approved for inclusion:
`authentication-setup`, `database-schema-design`, `api-documentation`.

Midway through design, the user asked whether a dedicated subagent should own
all frontend/UI/UX/web-development work — consolidating the existing 13
taste-skills, `make-interfaces-feel-better`, and the new frontend-concern
skills behind one dispatch point, rather than the main session picking a
skill itself each time. Investigation (later corrected during grilling — see below) found what
looked like two existing custom-agent conventions in this repo, but a
mechanical check of the actual files on disk found a third, which is the one
already proven working:

- **Heavy** (`~/.claude/Agents/<name>/`, e.g. `ba-agent`'s own project
  directory): a full separate mini-project — own `CLAUDE.md`, own `.wolf/`
  tracking, own `skills/`, opened as its own Claude Code session. Gitignored.
  Built for a self-contained deliverable-generation tool with its own
  memory/output pipeline, unrelated to this repo's own skill library.
- **Project-local** (`.claude/agents/*.md`, generated by
  `agent-team-architect`): meant for target projects *other than*
  `~/.claude` itself. Its own `SKILL.md` has an explicit self-targeting
  guard that stops and warns if pointed at `~/.claude`, since that would
  introduce a second, inconsistent in-repo agent convention. **Not used
  here** — see decision doc below.
- **Plugin-based** (`claude plugins init <name> --with agents` →
  `~/.claude/skills/<name>/agents/*.md` + `.claude-plugin/plugin.json`,
  auto-loaded as `<name>@skills-dir`): the mechanism that actually makes
  `ba-agent:ba` dispatchable as an `Agent` subagent_type today — confirmed
  by reading the real files, not the prose description. Git-tracked (unlike
  the heavy convention).

**Decision: use the plugin-based mechanism**, matching `ba-agent`'s proven
pattern exactly, rather than overriding `agent-team-architect`'s
self-targeting guard or standing up an unused heavy mini-project.
Full reasoning: `~/Desktop/frontend-design-subagent-mechanism-decision.md`.

## Scope

Build:

1. Six new skills under `~/.claude/skills/`, guidance-only (no generator
   scripts — LLMs are already competent at writing SQL/OpenAPI/auth code
   directly; a templating script would add maintenance burden for little
   gain).
2. One new subagent, `frontend-design`, scaffolded via
   `claude plugins init frontend-design --with agents`, owning all
   frontend/UI/UX work.
3. Small edits to `CLAUDE.md` (dispatch row) and `claude-infra-reference`
   (three new routing-table rows) to wire the subagent in.

Out of scope: the other ~75 skills in the supercent-io catalog (checked by
name against the existing library; the rest are either clearly redundant —
security-best-practices, code-review, debugging, testing-strategies,
task-planning, git-workflow, etc. — or off-stack for this user — PM
ceremonies, Firebase/Genkit, BigQuery, Vibe Kanban). `database-schema-design`
and `api-documentation` generator-script variants (deferred — guidance-only
per user decision). Any change to the heavy `~/.claude/Agents/` convention.

## New Skills

All six follow house convention (`superpowers:writing-skills`): `SKILL.md`
frontmatter `description` states only the triggering condition (never
workflow), target ≤1500 words in the main file, bulk reference material in
`references/`.

| Skill | Covers | Cross-refs / notes |
|---|---|---|
| `web-interface-guidelines` | Forms, animation, typography, images, navigation/state, touch/interaction, dark mode/theming, i18n, hydration safety, content & copy — from the Vercel checklist | Explicitly excludes ARIA/contrast/focus-state rules; points to `senior-engineering-partner/references/ui-design-and-accessibility.md` instead of duplicating them |
| `react-performance-patterns` | Bundle optimization (barrel-import detection), rendering efficiency (re-renders, async waterfalls), server-side bottlenecks — impact-ranked, before/after examples, from Vercel's 69-check list | — |
| `tailwind-css-patterns` | Utility recipes for cards/forms/grids/nav, dark-mode config, responsive/mobile-first patterns, common pitfalls (purged classes, dark-mode setup) | Framework-agnostic (React/Vue/Svelte) |
| `authentication-setup` | JWT/OAuth/RBAC/session management; secure defaults (short-lived access + longer-lived refresh tokens, bcrypt or argon2 password hashing, MFA support, DB-level token revocation); registration/login/refresh/logout flow patterns; social login (Google/GitHub/Microsoft) patterns | Ties into the existing security floor in `senior-engineering-partner` rather than restating it |
| `database-schema-design` | Normalization (1NF–3NF), relationship patterns, indexing strategy, denormalization tradeoffs, migration (up/down) structure — Postgres/MySQL/MongoDB/SQLite | Guidance/checklist only, not a DDL generator |
| `api-documentation` | OpenAPI spec structure and conventions; documenting auth patterns, pagination, rate limits, error codes; multi-language usage examples; avoiding doc/code drift | Generalized — not tied to one framework's doc-comment syntax |

## New Subagent: `frontend-design`

Scaffolded via `claude plugins init frontend-design --with agents`, matching
`ba-agent`'s proven registration pattern exactly: `~/.claude/skills/frontend-design/agents/frontend-design.md`
(frontmatter: `name`, `description`, `tools`, `model`, `color`, + system-prompt
body) plus `.claude/skills/frontend-design/.claude-plugin/plugin.json`,
auto-loaded as `frontend-design@skills-dir`. `model: sonnet` (per `model-routing`'s table — default tier; matches
`ba-agent`'s own choice, and `design-taste-frontend` already does most
aesthetic self-inference internally, so `frontend-design`'s own job is
mainly routing plus normal code editing, not open-ended architectural
reasoning). Dispatched as
`Agent(subagent_type: "frontend-design:frontend-design")`. Git-tracked, built
via the normal worktree → PR flow like any other skill-library change — not
`agent-team-architect` (which self-guards against targeting `~/.claude`) and
not the heavy `~/.claude/Agents/<name>/` convention (unused weight: this
subagent needs no standalone `CLAUDE.md` or `.wolf/` tracking of its own, it
just routes to skills that already exist).

**Owns:** every skill currently listed in `claude-infra-reference`'s taste-skill
routing table (the source of truth for exact membership — as of this spec:
`design-taste-frontend`, `design-taste-frontend-v1`, `minimalist-ui`,
`high-end-visual-design`, `industrial-brutalist-ui`,
`redesign-existing-projects`, `gpt-taste`, `image-to-code`,
`stitch-design-taste`, `imagegen-frontend-web`, `imagegen-frontend-mobile`,
`brandkit`) + `make-interfaces-feel-better` + the three new frontend-concern
skills (`web-interface-guidelines`, `react-performance-patterns`,
`tailwind-css-patterns`). Implementation should re-read the table at build
time rather than trusting this enumeration, in case it has changed since this
spec was written.

**Does not own:** `authentication-setup`, `database-schema-design`,
`api-documentation` — backend-domain skills, stay directly invocable by the
main session like any other skill.

**Behavior:** rather than duplicating the routing table in two places, the
subagent's system prompt instructs it to consult `claude-infra-reference`'s
routing table (updated with three new rows — see below) to decide which
skill(s) apply, and to preserve the existing "never stack more than one
frontend-aesthetic skill on the same task" constraint. Tool access mirrors
what frontend work actually needs: `Skill`, `Read`, `Edit`, `Write`, `Bash`,
`TodoWrite`, plus the specific `mcp__playwright__*` tool names (not a
blanket MCP grant — plugin agents can't declare their own `mcpServers:`, but
can list specific already-globally-registered MCP tools by name in `tools:`)
for visual verification, per the existing house rule that frontend changes
should be checked in a real browser before being reported done.

**Frontmatter correction (caught by a second-opinion review, then verified
against official docs — `code.claude.com/docs/en/sub-agents.md` and
`plugins-reference.md` — before accepting): 4 of that review's 5 claims were
right, 1 was wrong.** Confirmed true: a real `skills:` frontmatter field
exists (preloads listed skills into context at session start — used here
only for `claude-infra-reference`, since Step 1 of the routing logic always
reads it; the other 16 owned skills stay Skill-tool-invoked on demand rather
than all preloaded, which would be wasteful given several of those
`SKILL.md` files run 1000+ lines); plugin agents genuinely cannot use
`hooks`, `mcpServers`, or `permissionMode` (not used here regardless); a
real subagent nesting cap exists (default 3 layers) — moot here, since a
grep across all 13+ owned skills found none of them spawn subagents
themselves, and `frontend-design` doesn't need `Agent` tool access. Found
wrong: the review claimed `color` is undocumented/should be dropped —
it's actually a real documented field; kept, using a distinct color from
`ba-agent`'s `green` to visually distinguish them in tooling that renders
agent color.

## Wiring Changes

- **`CLAUDE.md` Process Layer table**: the row for "Writing or restyling
  frontend UI (landing page, portfolio, dashboard, any web/app visual
  design)" changes from routing the main session through
  `claude-infra-reference`'s table directly to dispatching
  `Agent(subagent_type: "frontend-design:frontend-design")` — but not
  unconditionally, and not silently:
  - **Threshold** (mirrors the existing ">3 files → Explore" pattern): a
    trivial, single-property tweak on an already-open file (e.g. "change
    this button's hover color") is handled directly by the main session, no
    subagent round-trip. Anything larger — a build, a redesign, multi-file
    work, or picking an aesthetic direction — is a candidate for dispatch.
  - **Confirm before dispatch**: unlike `Explore` (which auto-dispatches),
    the main session asks the user before actually deploying
    `frontend-design` for a qualifying task, rather than dispatching
    automatically. This is a deliberate deviation from the Explore pattern,
    per explicit user instruction during grilling.
  The `make-interfaces-feel-better` row is folded into the subagent's own
  responsibility (it already ran "layered on top" of whichever taste-skill
  fired; that composition now happens inside the subagent instead of being
  tracked by the main session) — but only for dispatched (non-trivial) work;
  a trivial inline tweak handled directly by the main session still runs
  `make-interfaces-feel-better` as before if warranted, since no subagent
  was involved.
- **`claude-infra-reference` routing table**: three new rows added for the
  concern-based skills, each framed as "layers alongside `make-interfaces-feel-better`
  after a taste-skill build, not instead of one" — the same composition
  pattern already established for `make-interfaces-feel-better` itself:
  - `web-interface-guidelines` — any frontend build/review, correctness pass
    (forms/animation/typography/hydration/etc.)
  - `react-performance-patterns` — React/Next.js projects only, performance
    pass
  - `tailwind-css-patterns` — Tailwind projects only, pattern reference
- The three new backend skills need no routing-table changes — they have no
  existing family to conflict with; each is triggered directly by its own
  `SKILL.md` description like any standalone skill.
- **`brand` hard-gate handoff, updated not dropped**: `claude-infra-reference`
  currently says "for a UI build that must carry the user's own brand, run
  `brand` first for the Spec Card, then feed those constraints into whichever
  `taste-skill` skill applies." That check stays a main-session
  responsibility (unchanged — it's a pre-check before any output creation,
  orthogonal to which skill/subagent does the work), but the hand-off target
  changes: the Brand Spec Card's constraints get folded into the dispatch
  prompt text passed to `Agent(subagent_type: "frontend-design:frontend-design")`
  instead of being fed directly to a directly-invoked taste-skill.

## Testing / Verification

Skills are markdown, not executable code — "testing" here means:

- Each new `SKILL.md` passes the same red-flag checks `writing-skills`
  applies to any skill: no placeholder content, description states only
  triggering conditions, no workflow leaked into the description.
- The `frontend-design` subagent definition is validated against
  `agent-team-architect`'s Phase 6 checklist criteria (see its
  `references/validation-checklist.md`) even though that skill isn't used to
  scaffold it — the criteria (description triggers correctly and not on a
  near-miss; dry-run dispatch succeeds) are construction-mechanism-agnostic.
- **Registration check first** (lighter than a full dispatch): in the
  session *after* implementation, type `@frontend-design:` and confirm
  `frontend-design:frontend-design` appears in the typeahead — the actual
  documented signal that plugin registration succeeded (there is no `claude
  plugins list` command). The `/plugin` in-session manager is a secondary
  way to check plugin status.
- **Description-as-routing-rules check**: before considering the agent
  definition done, test its `description` field against 5-10 realistic
  sample requests spanning different owned skills (e.g. "build a landing
  page" → `design-taste-frontend`; "this app needs a Notion-like look" →
  `minimalist-ui`; "audit my existing dashboard's UI" →
  `redesign-existing-projects`; "polish the hover states on this button" →
  `make-interfaces-feel-better`; "why is this React page slow" →
  `react-performance-patterns`) and confirm each would plausibly trigger
  dispatch, since at 16+ owned skills a vague description produces
  unreliable routing.
- A smoke-test dispatch: run one real frontend task through
  `Agent(subagent_type: "frontend-design:frontend-design")` and confirm it
  picks a sensible skill combination (e.g. a greenfield landing page task
  should select `design-taste-frontend` + `web-interface-guidelines`, not
  stack a second aesthetic-locked skill), and that it routes to the
  *correct* skill specifically, not just *a plausible* one — this is the
  real risk area at this skill count, more so than context budget. **This
  cannot happen in the same session that creates the plugin** — per this
  repo's own documented learning, the Agent tool's available-subagent-types
  list (like the Skill tool's available-skills list) is computed once at
  session start, so a newly-registered plugin agent throws `Unknown agent
  type` until the next session. The smoke test is the first thing to run in
  the session *after* implementation.

## Risks / Open Questions Resolved During Brainstorming

- *Redundancy with existing a11y content* — resolved by explicit exclusion +
  cross-reference rather than duplication.
- *File-size bloat* — resolved by keeping all new content as standalone
  skills with `references/` subfiles, not inlined into `design-taste-frontend`.
- *Which of the 78 supercent-io skills are worth pulling* — resolved by
  targeted fetch-and-review of a shortlist rather than blind bulk import; one
  candidate (`web-design-guidelines`) was found to be a duplicate and
  dropped.
- *Generator scripts vs. guidance-only* for the backend skills — resolved in
  favor of guidance-only per user decision.
