# Incorporate Blume: local harness docs site

**Date:** 2026-07-15
**Status:** Approved, grilled

## Summary

Incorporate [Blume](https://github.com/haydenbleasel/blume) (zero-config Markdown/MDX docs-site generator, npm package `blume`, built on Astro/Vite/Tailwind v4, requires Node 22.12+) into `~/.claude` for two purposes:

1. A **global CLI install** so Blume is available to scaffold docs sites in any future project, independent of this harness work.
2. A **local, personal-reference docs site** (`docs-site/`) inside `~/.claude` that documents the "thin-harness, fat-skills" system — skills, CLAUDE.md structure, OpenWolf integration — browsable via `blume dev`.

## Goals

- `blume` runnable globally from any shell/project on this machine.
- A working local docs site at `~/.claude/docs-site/` covering, at minimum: a home page, an auto-generated reference page per skill (including nested reference files, e.g. `senior-engineering-partner/references/*.md`), and stub overview pages for CLAUDE.md's structure and the OpenWolf integration.
- A repeatable sync mechanism so the skills reference section doesn't go stale as skills are added/edited.
- Content authored three ways, coexisting in the same content tree: auto-pulled (sync script), hand-authored or Claude-drafted on instruction, and linked-not-duplicated (pointing at source-of-truth files rather than mirroring them).
- A `docs-site/README.md` explaining how to regenerate/extend the site, so the mechanism doesn't have to be re-derived from this spec later.

## Anti-goals

- **Not** a published/public site. No git remote exists on this repo today (confirmed via `git remote -v`), and none will be added as part of this work. No GitHub Pages, no deploy workflow, no server-output adapter (Vercel/Netlify/Node/Cloudflare) — `blume build` output, if used at all, stays local.
- **Not** wired into the root `package.json` (`dotclaude-hooks-lint`) — that package is narrowly scoped to linting hook scripts and stays that way.
- **Not** full prose for the Harness Overview / OpenWolf pages in this pass — those ship as stubs (title, a few bullets, a link to the source of truth). Full prose is written later, incrementally, on demand.
- **Not** a full content migration otherwise. Deeper material (brain MCP internals, knowledge-graph internals) is explicitly deferred to later, incremental additions.
- **Not** using Blume's Ask AI assistant, hosted MCP server, or remote/custom content-source backend in this pass — those are live-service/network-facing features that don't fit "personal local reference" and add complexity not needed yet.
- **Not** generating `meta.ts` nav-ordering files — default alphabetical ordering is used for this pass.

## Architecture

### Install

- Global: `npm install -g blume` (npm chosen for consistency with the root repo's existing npm-based tooling; `bun`/`pnpm` are also available on this machine if a future project prefers them, but the global install itself is npm).
- Project-local: **`blume init` runs first**, inside `docs-site/`, as an interactive scaffold — it generates `package.json`, `blume.config.ts`, and the initial content folder per its own zero-config workflow. Customizations (sync script wiring, `.gitignore` entries, denylist logic, README) are layered on top afterward rather than hand-built ahead of it. Once scaffolded, the `blume` devDependency in `docs-site/package.json` is left on a **caret range** (e.g. `^1.x.x`), not pinned exact — this is a single-user local tool with no CI/deploy pipeline depending on reproducibility.

### Directory layout

```
~/.claude/
  docs-site/
    README.md              # how to regenerate/extend this site
    package.json            # generated by `blume init`, then customized (sync script, caret version)
    blume.config.ts          # generated by `blume init`
    scripts/
      sync-content.mjs       # auto-pull mechanism (see below)
    content/                  # exact subpath(s) per blume init's scaffold
      skills/
        <skill-name>.md        # auto-generated, one per skill (sync script output)
        <skill-name>/
          <nested-file>.md      # auto-generated sub-pages for nested reference files
      overview/*.md              # stub pages, one per CLAUDE.md numbered section
      openwolf.md                  # stub page, OpenWolf explainer
      index.md                      # home page
```

The exact content-folder naming/nesting will follow whatever `blume init`'s interactive scaffold produces — confirmed during implementation, not guessed here.

### `.gitignore` additions (repo root)

- `docs-site/node_modules/`
- `docs-site/dist/`
- `docs-site/.astro/` (Blume's generated build directory)

### Content sync mechanism

`docs-site/scripts/sync-content.mjs`:

- Reads every `skills/*/SKILL.md`. **Skips silently** any skill directory with no `SKILL.md` at all (e.g. `ba-agent`, which only contains an `agents/` subfolder — it's an agent definition, not a skill). **Warns (does not fail)** if a `SKILL.md` exists but is missing the `name` or `description` frontmatter field.
- Each `SKILL.md` has YAML frontmatter with `name` and `description` only — no `title`, which Blume's page frontmatter needs. The script derives `title` from `name` and carries `description` through unchanged.
- Writes the transformed page to `docs-site/content/skills/<skill-name>.md`.
- **Also walks each skill directory for other `.md` files** (e.g. `senior-engineering-partner/references/*.md`, `domain-modeling/CONTEXT-FORMAT.md`, `teach/*-FORMAT.md`) and writes each as a nested sub-page under that skill (`docs-site/content/skills/<skill-name>/<file>.md`), so they appear as child pages in the nav rather than flat top-level entries. **Excludes a fixed denylist** of OSS-repo-scaffolding filenames that aren't actual skill content: `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`, `MAINTAINERS.md`, `CHANGELOG.md`, `LICENSE*`.
- No `meta.ts` generation — pages render in default (alphabetical) order.
- Idempotent — safe to re-run at any time. Wired up as `npm run sync` inside `docs-site/`, and as a `predev`/`prebuild` step so the skills section is regenerated automatically before `blume dev`/`blume build`.
- Writes only under `docs-site/content/skills/` — never touches hand-authored content elsewhere in the tree, so there's no risk of the sync script clobbering manually written pages.

### Page inventory (this pass)

- **Home** (`content/index.md`) — landing page with a short intro and nav.
- **Skills Reference** (`content/skills/**/*.md`, auto-generated, ~19 top-level pages + nested sub-pages for skills with reference files) — one per skill via the sync script, denylist-filtered.
- **Harness Overview** (`content/overview/*.md`, stub pages, ~7 pages) — one per CLAUDE.md numbered section (Core Philosophy, Process Layer, Infrastructure Layer, New Project Bootstrap, Personal Knowledge Layer, Knowledge Graph, Reference Pointers). Each stub has a title, a few bullets, and a link back to the actual CLAUDE.md section as the source of truth — full prose is written later, on demand.
- **OpenWolf Integration** (`content/openwolf.md`, stub page) — points at `.claude/rules/openwolf.md` and the OpenWolf-related parts of CLAUDE.md Section 3, to be filled in with a real synthesis later.
- **`docs-site/README.md`** — explains `npm run sync`, where hand-authored content lives, and the denylist convention, for future reference.

Deferred to later, incremental passes: full prose for overview/OpenWolf pages, brain MCP internals, knowledge-graph internals.

## Tooling touchpoints (confirmed during research, no action needed beyond what's listed above)

- **Pre-commit hook** (`.githooks/pre-commit`): only targets staged `*.sh` files (shellcheck) and staged `^(hooks|\.wolf/hooks)/.*\.js$` files (eslint) — MDX/content files and `docs-site/scripts/*.mjs` won't match either glob, so no hook changes needed. `gitleaks protect --staged` still scans all staged files regardless of path, which is why generated build artifacts (`dist/`, `.astro/`) must be gitignored rather than ever staged.
- **Submodules** (`langsmith-plugin`, `superpowers`, `skills/senior-engineering-partner`): each has an independent dependency tree; `docs-site/`'s own `package.json` doesn't interact with them.
- **Node**: v24.17.0 installed, satisfies Blume's 22.12+ requirement. No `.nvmrc` needed.

## Testing / verification

- After `blume init` + sync script + stub content: run `blume dev` inside `docs-site/`, confirm the site starts and the nav renders all sections (Home, Skills Reference with nested sub-pages, Harness Overview, OpenWolf).
- Spot-check a handful of auto-generated skill pages (including at least one skill with nested reference files, e.g. `senior-engineering-partner`) render with correct title/description and body content.
- Confirm `ba-agent` is silently skipped (no page, no error) and that a `SKILL.md` with missing frontmatter produces a warning, not a crash.
- Confirm denylisted files (e.g. `senior-engineering-partner/CONTRIBUTING.md`) do not appear as pages.
- Confirm internal links (overview stubs → CLAUDE.md source, OpenWolf stub → `.claude/rules/openwolf.md`) resolve.
- Re-run `npm run sync` after editing a `SKILL.md` and confirm the corresponding page updates, and that hand-authored/stub pages are untouched.
