# Claude Infra Reference

Lookup-style reference detail moved out of the global `CLAUDE.md` (which now only carries a one-line pointer to this skill) — read this on demand when doing one of the specific tasks named in the description above, not as passive session-wide context.

## Custom Agents
- **Location:** `~/.claude/Agents/<agent-name>/` — each has its own CLAUDE.md, skills/, templates/, outputs/, scripts/
- **Open with:** `claude ~/.claude/Agents/<agent-name>/`
- **Gitignore note:** `Agents/` is gitignored — edit files there directly (no worktree needed). Only `skills/` and `hooks/` under `~/.claude` are git-tracked.
- **Project-local teams are a different convention:** the `agent-team-architect` skill generates `.claude/agents/` + `.claude/skills/` inside a *target project* (not under `~/.claude/Agents/`), for repeatable domain-specific subagent teams that travel with the project they serve. It does not use this centralized convention and is not opened via `claude ~/.claude/Agents/<name>/` — it's invoked from within the target project itself.

## Custom Plugin Registration
- **Local plugins** (no upstream git repo): `claude plugins init <name> --with agents` → scaffolds at `~/.claude/skills/<name>/`, auto-loads as `<name>@skills-dir` — no marketplace or install step needed
- **YAML agent frontmatter:** quote any `description:` value that contains `: ` (colon-space) or the parser silently drops all frontmatter
- **Do NOT** manually edit `installed_plugins.json` — source type validation blocks loading even with a valid `installPath`; use `claude plugins validate <path>` to check before wiring
- **Submodule ≠ registered plugin:** a skill file existing inside a git submodule (e.g. `superpowers/skills/<name>/`) does not make it invocable via the Skill tool — check `~/.claude/plugins/installed_plugins.json` for the plugin name before assuming a submodule's skills are live. Fix for an unregistered local-repo plugin (needs a `.claude-plugin/marketplace.json`, which `superpowers` has): `claude plugin marketplace add <path-to-repo>` then `claude plugin install <plugin>@<marketplace-name>`. A restart is required afterward — skill discovery is computed at session start, so the newly installed skill will still throw `"Unknown skill"` in the same session even after a successful install.

## Brand / Document Skill Convention
- **Brand/structure separation:** In document skill briefs, never hardcode brand values (hex codes, font names, sizes) — say "Apply Brand Spec Card" and let `~/.claude/brand/brand-guide.md` be the only source. Only format-structural constraints (DXA widths, slide count, `No \n in paragraphs`) belong in the skill file itself.
- **Brand source of truth:** `~/.claude/brand/brand-guide.md` → read at runtime by `~/.claude/skills/brand/SKILL.md` → outputs Brand Spec Card → referenced by all document briefs. Updating brand-guide.md propagates everywhere automatically.

## Browser Automation
- A `playwright` MCP server (`@playwright/mcp`) is registered in `~/.claude.json`'s top-level `mcpServers` (the mechanism that's actually live — not `mcp_servers.json`, which is disconnected from Claude Code's config surface) for interactive browser automation (navigate/click/type/screenshot/DOM read). Distinct from the `html-export` skill (static screenshot/PDF export of a finished page); use `playwright` when you need to actually interact with a running app. Note: `html-export`'s own Playwright pipeline is currently broken (ESM/CJS conflict in `~/.claude/package.json` + no local `playwright` npm package) — needs a fix before it works again.

## External Skill Integrations (mattpocock/skills)
- Installed via the `npx skills` CLI (`npx skills@latest add mattpocock/skills <skill-names...> --global --copy -y`; the `-s/--skill` flag does not reliably filter in non-interactive mode — pass skill names positionally, or install everything and prune unwanted ones with `npx skills remove <names...> --global -y`). Installed as real copies (`--copy`), not symlinks into `~/.agents/skills/`, so they live fully inside this git repo like every other custom skill.
- **grill-me** (user-invoked, `/grill-me`) + **grilling** (model-invoked primitive it wraps) — relentless one-question-at-a-time interview to stress-test a plan. `grilling` may also be reached for automatically by other skills; `grill-me` never invokes anything except `grilling`.
- **codebase-design** (model-invoked) — deep-module design vocabulary (interface/seam/adapter/deletion test). Installed standalone, not merged into `senior-engineering-partner`; reach for it alongside `senior-engineering-partner` REVIEW:/EXPLAIN: modes when the topic is module/interface shape, not general code correctness. Includes `DEEPENING.md` and `DESIGN-IT-TWICE.md` references.
- **domain-modeling** (model-invoked) — active glossary/ADR discipline, writes `CONTEXT.md` and `docs/adr/`. Distinct from `understand-anything:understand-domain`, which only reads existing code into a graph and never writes back to the repo. Includes `CONTEXT-FORMAT.md` and `ADR-FORMAT.md` references.
- **teach** (user-invoked, `/teach`) — stateful multi-session tutoring workspace (`MISSION.md`, `lessons/`, `reference/`, `learning-records/`, `assets/`). Personal/educational output — exempt from the `brand` hard-gate. Treats the current directory as the workspace: only invoke from a dedicated learning directory, never from `~/.claude` itself.
- **handoff** (user-invoked, `/handoff`) — locally modified from upstream: saves to `.wolf/handoffs/<UTC-timestamp>-handoff.md` instead of the OS temp dir, for discoverability via OpenWolf and worktree-friendliness. Because it's modified, re-running the install for `handoff` will overwrite the local edit — reapply the `.wolf/handoffs/` change after any upstream update.
- **Note:** `grill-me`, `teach`, and `handoff` are enforced user-invoked at the tool level — calling `Skill({skill: "grill-me"})` etc. throws `disable-model-invocation` and fails. They can only be triggered by the user typing the slash command directly; Claude cannot self-invoke or self-verify them.
- Not installed from this repo (considered and skipped): `ask-matt`, `code-review`, `diagnosing-bugs`, `grill-with-docs`, `implement`, `improve-codebase-architecture`, `prototype`, `setup-matt-pocock-skills`, `tdd`, `to-issues`, `to-prd`, `triage`, `writing-great-skills`, and the `general/` category skills — out of scope for this integration pass, revisit individually if a need arises.

## External Skill Integrations (taste-skill / Leonxlnx)
- Installed via the same `npx skills` CLI as mattpocock's: `npx skills@latest add https://github.com/Leonxlnx/taste-skill <install-names...> --global --copy -y`. **Caveat found during install: `--global` resolves to the actual `~/.claude/skills/` path regardless of `cwd`, bypassing worktree isolation entirely** — running the install from inside a worktree still writes into the main checkout. If installing more from this repo later, either run it directly in the main checkout, or run it from a worktree and then `mv` the new folders from the main checkout's `skills/` into the worktree's before committing (what was done here).
- All 13 skills from the repo were installed (11 requested install names plus `design-taste-frontend-v1`, which the CLI pulled in as a paired dependency of the default `design-taste-frontend`). 67.9k-star MIT-licensed repo with a real `.claude-plugin/marketplace.json`; CHANGELOG shows genuine iteration (e.g. the v2 em-dash ban was added after it was "the single most-violated stylistic Tell in pre-v2 testing"). `design-taste-frontend-v1` was later removed (bloat audit, 2026-08-15) after confirming zero real invocations anywhere in the repo — `design-taste-frontend` (v2) is the only backward-compat path now.
- **These skills carry real conflict risk with each other.** Several are full aesthetic-locked system prompts (specific hex codes, specific font bans, persona framing) covering overlapping ground — installing more than one into context for the same task can produce contradictory instructions (e.g. two different banned/required font lists). Route deliberately using the table below; do not let more than one frontend-aesthetic skill apply to the same piece of work.

**Routing table — which skill for which situation (Claude Code, the default target):**

| Situation | Use | Notes |
|---|---|---|
| New landing page / portfolio / marketing site, aesthetic not yet decided | `design-taste-frontend` | Default choice. Self-infers page kind, audience, and vibe, then sets its own layout/motion/density dials — don't stack another aesthetic-locked skill on top of it. |
| User already named a specific aesthetic | Pick exactly ONE, in place of `design-taste-frontend`, not in addition to it: `minimalist-ui` (Notion/Linear editorial), `high-end-visual-design` (premium/calm/expensive agency feel), or `industrial-brutalist-ui` (Swiss/mechanical/terminal) | These hardcode their own palette and font-ban list — combining with `design-taste-frontend`'s dial system or with each other is the contradiction case above. |
| Existing project's UI needs auditing/fixing rather than a greenfield build | `redesign-existing-projects` | Audit-first, works with the current stack, does not rewrite. This is the one for polishing an already-built app (e.g. a dashboard-style project). |
| Any task (UI or not) where output is getting truncated or placeholder-stubbed | `full-output-enforcement` | General-purpose completeness discipline, not UI-specific; complements `verification-before-completion` rather than replacing it. |
| Working in Codex/ChatGPT rather than Claude Code | `gpt-taste`, `image-to-code` | Both explicitly written for Codex (GSAP-heavy, Python-simulated randomization workaround for GPT's layout bias). Not the right pick for a Claude Code session — only relevant if the user is pasting the skill into another tool. |
| Working in Google Stitch | `stitch-design-taste` | Generates a `DESIGN.md` for Stitch specifically; irrelevant outside that tool. |
| Deliverable is reference images only (no code), for feeding into an external image generator | `imagegen-frontend-web`, `imagegen-frontend-mobile`, `brandkit` | Image-output-only skills. Not directly actionable in this environment without an image-generation tool wired up — treat as reference material for a separate pass through ChatGPT Images/Codex, not something to invoke standalone here. |
| Any frontend build or review needs a correctness pass (forms, animation, typography, images, nav/state, touch, dark mode, i18n, hydration safety) | `web-interface-guidelines` | Layers alongside `make-interfaces-feel-better` after a taste-skill build, not instead of one. Deliberately excludes ARIA/contrast — see `senior-engineering-partner`'s accessibility reference for those. |
| Project is React or Next.js and performance is a concern (re-renders, bundle size, slow SSR) | `react-performance-patterns` | React/Next.js projects only. Layers alongside the build, same composition pattern as `make-interfaces-feel-better`. |
| Project uses Tailwind CSS and needs utility-class pattern reference | `tailwind-css-patterns` | Tailwind projects only. Pattern reference, not aesthetic direction — defer to whichever taste-skill picked the visual direction. |

- **Interaction with the `brand` hard-gate:** `brand` governs the user's own established visual identity (colors/fonts sourced from `~/.claude/brand/brand-guide.md`) for branded deliverables. `taste-skill`'s skills govern raw frontend craftsmanship (layout, motion, spacing, anti-slop patterns) and are complementary, not a substitute. For a UI build that must carry the user's own brand, run `brand` first for the Spec Card. If the work is being dispatched to the `frontend-design` subagent (see the Custom Agents section above), fold the Spec Card's constraints into the dispatch prompt text; otherwise feed them directly into whichever `taste-skill` skill applies from the table above. For a project with no brand identity to apply (internal tool, personal project), skip `brand` and go straight to the table.

## External Skill Integration (make-interfaces-feel-better / jakubkrehel)
- Installed via `npx skills@latest add jakubkrehel/make-interfaces-feel-better --global --copy -y` — same `--global` home-anchoring caveat as the taste-skill install above (bypasses worktree isolation; run directly in the main checkout, or `mv` the new folder out of the main checkout into the worktree before committing). MIT-licensed, 2.5k stars, single skill (not a multi-skill repo like the two above).
- **Not part of the taste-skill family and not routed through its table.** The taste-skill variants are aesthetic-locked system prompts that decide layout/palette/motion direction for a build; this skill is a narrow, detail-level *review pass* — border radius, optical alignment, shadows vs. borders, animation easing/timing, icon stroke weight and state handling, hit-area sizing, tabular numbers, text wrapping. It has no opinion on overall visual direction, so it doesn't conflict with any of the 13 variants above — run it *after* whichever taste-skill (or hand-written) UI is otherwise done, as a polish/correctness pass, not instead of one.
- **When to invoke:** any time UI/frontend code is being built or reviewed for interface polish — hover/focus/active/loading/empty states, micro-interactions, enter/exit animations. Supports `quick` (primary path + high-traffic states, HIGH/MEDIUM only, 5-finding cap) and `full` (entire scope, all categories, 15-finding cap) modes; `full` is the default when no mode is given. Findings are grouped by principle with Severity/Location/Before/After/Why columns, plus a Considered-but-Rejected section and an explicit Block/Needs changes/Approve verdict — read the verdict, not just the table, before treating a UI change as done.
- **Slash usage:** `/make-interfaces-feel-better`, `/make-interfaces-feel-better quick`, `/make-interfaces-feel-better full pricing page`.
