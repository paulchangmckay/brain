## Key Learnings — NHL Stats Project

- 2026-07-02: The stats REST API (`api.nhle.com/stats/rest/en`) returns `avgToi` as decimal seconds string (e.g. "1379.12" = 22:59/game) while the landing API returns it as "MM:SS". Both land in the same DB column. Normalize at display time: `float(val) → f"{int(s//60)}:{int(s%60):02d}"`, fallback to raw string if float() raises.
- 2026-07-02: `upsert_player_stub()` only writes 5 fields. Players loaded this way are bio-incomplete (null height/weight/birth_date/birth_country). The landing API returns `heightInInches`, `weightInPounds`, `birthDate`, `birthCountry` — must be explicitly extracted and added to `upsert_player_enrichment()`'s UPDATE or they'll never be written.
- 2026-07-02: ETL enrichment WHERE clauses that combine `is_active` AND `enriched_at` conditions create permanent dead zones for partial-state rows. Pattern: use orthogonal single-field conditions: `WHERE enriched_at IS NULL OR (is_active=1 AND enriched_at < datetime('now','-7 days'))` — each branch independently covers its case.

## Learning: 2026-07-21 — Blume routing requires index.md, not <slug>.md, for any page with nested sibling content
When a page needs relative-linked sibling files (e.g. a skill's SKILL.md plus its reference/*.md files), Blume only resolves relative links correctly if the linking page is written as `<slug>/index.md` — a flat `<slug>.md` sitting one directory above its own nested files breaks relative resolution in both directions (parent->child and child->parent), since Blume resolves relative links against the *directory* the source file physically lives in, not its route slug. Confirmed empirically: writing two files as `_x/index.md` + `_x/other.md` with mutual `./`-relative links resolved cleanly; the flat-file equivalent did not. Bug fix in docs-site/scripts/pull-skills.mjs (bug-118): `syncSkills` now only uses the flat form when a skill has zero nested markdown files.
**How to apply:** if `docs-site/scripts/pull-skills.mjs` is touched again, or any other Blume-based static content is generated programmatically, apply the same rule — co-locate a page with its nested/sibling content on disk, don't hoist it out to a shorter path, or relative links inside will silently 404 (`blume validate --strict` catches this).

## Key Learnings (2026-07-25 — markitdown skill)
- `pipx install '<pkg>[extra]'` (no explicit `--python`) can silently install a very old, functionally-crippled version of a package with no error message, if the latest version's extras have a sub-dependency with no wheel for the default Python (here: Python 3.14.5). `pip`'s resolver backtracks through older releases of the *top-level* package (not just the sub-dependency) until it finds one whose extras happen to have looser/older pins that resolve — landing on `markitdown==0.0.2` instead of the real `0.1.6`. Always verify the actually-installed version explicitly after an unpinned install of a package with heavy optional extras, not just that the command exited 0.
- `EnterWorktree`'s native worktree creation uses `worktree.baseRef` (default `fresh`), which branches from **`origin/<default-branch>`**, not local `main` — so any local-only commits on `main` that haven't been pushed yet (e.g. spec/plan docs committed directly to `main` during brainstorming, per this repo's own established pattern) are invisible in a freshly created worktree. Fix locally with `git rebase main` from inside the worktree (a purely local operation, no push needed) rather than pushing `main` to origin mid-task just to unblock the worktree. Symmetric gotcha at merge time: squash-merging the feature branch's PR creates a new commit on `origin/main` whose only parent is whatever `origin/main` was at merge time — if local `main` had already-diverged unpushed commits (as here), local `main` and `origin/main` end up with genuinely divergent histories even though the *content* is a strict superset. Reconcile with a plain `git merge origin/main` (safe — resolves cleanly when content is identical/additive) rather than `git reset --hard`.
- `subagent-driven-development` and `executing-plans` are not currently dispatchable via the `Skill` tool — confirmed by trying both bare and `superpowers:`-prefixed names, both returning "Unknown skill." This matches the plugin-cache drift flagged at session start (`installed_plugins.json` records an older `superpowers` commit than the actual submodule HEAD). Workaround: the skill files still exist on disk at `superpowers/skills/<name>/SKILL.md` — `find`/`Read` them directly and follow the instructions manually (including their referenced `scripts/*` helpers like `task-brief`/`review-package`, which work fine invoked directly). Don't block a subagent-driven-development execution on this — it degrades gracefully to "read and follow manually."

## Key Learnings (2026-07-27 — context-mode MCP integration, worktree merge)
- Rebasing a worktree branch onto local `main` before creating a PR (the documented workaround for "EnterWorktree branches from origin, not local main") has a consequence not previously called out: a subsequent `gh pr merge --squash` then squashes the *entire* diff between origin/main and the branch tip into one commit — which includes every other unpushed local-main commit that came along via the rebase, not just the branch's own commits. Confirmed directly: PR #26 ("Add context-tools skill") squash-merged in `.wolf/anatomy.md`/`buglog.json`/`cerebrum.md`/`memory.md`/`observations.md` updates, three unrelated skill symlinks, and a full unrelated spec (`2026-07-27-agent-team-architect-design.md`) — none of which had anything to do with context-mode, none of which went through their own review. Worse, that spec file was mid-edit by a *different concurrent session* (a second, locked worktree `feature+27-agent-team-architect` was found still active) — the squash captured a stale pre-grilling snapshot of it, which then produced a real add/add merge conflict on the next `git merge origin/main` back into local `main` (resolved with `git checkout --ours`, since local main's copy was the newer, already-more-complete version; the concurrent session's own worktree was left untouched). None of the swept-in content was wrong, just unreviewed-as-a-unit and misleadingly attributed to an unrelated PR title. Lesson: before running `gh pr merge --squash` on a worktree branch that was rebased onto local main, check `git diff --stat <old-origin-main-sha>..<branch-tip>` first — if it's larger than the branch's own commits account for, either push local main's other pending commits as their own separate PR(s) first, or accept and document that the merge will bundle them.

## Key Learnings (2026-08-09 — plugin install session)
- When a worktree-merge stash-conflict lands on `.wolf/memory.md` (or any file another session's background hooks write to), don't assume the conflict is a simple two-sided diff to hand-resolve — check `git diff HEAD -- <file>` fresh, more than once if needed, before touching it.
